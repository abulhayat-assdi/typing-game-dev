# PHASE 3 — CROSS-BATCH CLAN WAR, SEASONS, ECONOMY & LIVE EVENTS

## 1. Phase 3 Vision

Phase 3 turns batches into a competitive social universe.

A batch is represented as a clan. Different batches from the same course—or batches from different courses—can compete when authorized by the admin.

## 2. Clan War Lifecycle

### Step 1 — Challenge
Clan A sends an invitation to Clan B.

### Step 2 — Acceptance
Clan B leader/co-leader accepts or declines.

### Step 3 — Preparation
Admin-configured preparation window, e.g. 2–3 hours.

### Step 4 — Battle Window
Admin configures the battle window, e.g. 3–5 hours.

### Step 5 — Participation
Every eligible member gets a limited number of validated attempts.

### Step 6 — Scoring
Aggregate the configured metrics:
- valid XP score
- WPM
- accuracy
- completion count
- best run
- participation bonus

### Step 7 — Result
Winning clan receives:
- clan XP
- clan coins
- player XP
- player coins
- badges/titles
- seasonal points

### Step 8 — Record
War result is permanent and appears in clan history.

## 4. Cross-Course Competition

Allowed examples:
- Sales & Marketing Batch A vs Sales & Marketing Batch B
- Sales & Marketing Batch A vs Telesales Batch C
- Any approved batch vs any approved batch

The UI must clearly show:
`Course → Batch → Clan`

## 5. Clan Leadership

Roles:
- Clan Leader
- Co-Leader
- Member

Permissions:
- Leader: invite, accept, configure clan profile, nominate co-leaders
- Co-Leader: approve invitations, start approved clan activities
- Member: participate, request help, contribute scores

Admin override is always available.

## 6. Clan Economy

Wallet types:
1. Personal Coins
2. Clan Coins
3. Seasonal Points

Do not mix ledgers.

### Personal Coins
Used for:
- cosmetics
- profile items
- approved support items

### Clan Coins
Used for:
- clan banners
- clan effects
- team upgrades
- event entries where allowed

### Seasonal Points
Used only for:
- seasonal ranking
- seasonal rewards

## 7. Clan Shop

## 8. Seasonal System

- season name
- start
- end
- eligible games
- eligible clans
- leaderboard reset policy
- seasonal rewards
- archive policy

A season can contain:
- weekly wars
- weekend cups
- daily quests
- clan raids
- grand championship

## 9. Clan War Anti-Abuse

Mandatory:
- server-side score verification
- attempt limits
- suspicious score detection
- rate limits
- impossible-WPM detection
- replay/sample auditing
- duplicate submission prevention
- device/session anomaly checks
- admin review queue

Never trust the browser to calculate final competitive scores.

# SHARED ENGINE — REQUIRED ACROSS ALL THREE PHASES

## A. Core Game Engine

Do not build 240 games as 240 unrelated React pages.

Build a reusable game engine with:
- Game Definition
- Game Renderer
- Input Rules
- Prompt Generator
- Difficulty Profile
- Scoring Function
- Reward Policy
- Unlock Policy
- Audio Pack
- Visual Pack
- Result Validator

Most games should be configuration-driven.

### Example Concept

```ts
type GameDefinition = {
  id: string;
  slug: string;
  worldId: string;
  mode: "letter" | "word" | "sentence" | "number" | "symbol" | "mixed";
  mechanic: string;
  difficulty: "beginner" | "intermediate" | "expert";
  durationSec?: number;
  promptSource: string;
  scoringProfile: string;
  unlockRule: UnlockRule;
};
```

## B. Scoring

Keep raw metrics separate from reward calculations.

Raw:
- elapsed_ms
- chars_typed
- correct_chars
- incorrect_chars
- corrections
- words_completed
- accuracy
- raw_wpm
- effective_wpm

Derived:
- score
- XP earned
- coins earned
- badge unlocks

This lets the scoring model evolve without corrupting raw records.

## C. WPM

Default:
`WPM = (correct_characters / 5) / minutes`

Store both raw WPM and effective WPM.

Accuracy:
`accuracy = correct_characters / total_typed_characters * 100`

## D. Database Ledger Rules

XP, coins, seasonal points and rewards must be append-only ledgers.

Never only store:
`users.xp = 1200`

Instead store:
- transaction ID
- user ID
- source
- amount
- balance_after
- timestamp
- reference ID
- metadata
- created_by/system

Then maintain cached balances for performance.

## E. RLS

Every table containing student-owned information needs an explicit RLS policy.

Public/batch-visible:
- display name
- roll
- level
- public badges
- public records
- leaderboard metrics

Private:
- email
- password/auth metadata
- internal moderation notes
- private analytics
- ad/reward verification metadata

## F. API Boundaries

Client may request:
- start game
- submit attempt
- request unlock status
- view leaderboard
- view profile
- request help
- join competition

Server validates:
- identity
- batch membership
- game availability
- unlock requirements
- attempt limits
- timing
- score
- reward

## G. Caching

Recommended:
- Cache public game definitions at the edge.
- Cache world map metadata.
- Cache public leaderboard snapshots briefly.
- Never edge-cache private student data without correct cache keys and privacy controls.

## H. R2

Use R2 for:
- avatar originals
- optimized avatar variants
- game illustrations
- world backgrounds
- badges
- cosmetics
- sound
- promotional assets

Never store:
- passwords
- auth secrets
- student private exports
- unencrypted sensitive data

## L. Backup & Recovery

For self-hosted Supabase, backups are the operator's responsibility. Production deployment must include automated PostgreSQL backups, retention, restore testing, disk monitoring and disaster-recovery procedures before the platform becomes business-critical.

## M. Launch Strategy

Although the code is developed in three phases, launch all planned capabilities behind feature flags.

Example:

```text
PHASE_1_CORE = true
PHASE_2_ADAPTIVE = true
PHASE_2_REWARDED_ADS = false
PHASE_3_CLAN_WARS = false
PHASE_3_SEASONS = false
```

This allows the entire codebase to be shipped while advanced systems are activated safely.

## N. Critical Product Rule

The platform must never make the learner feel forced to type.

Every session should answer:

**What is my mission?**
**Why should I care?**
**What do I unlock next?**
**What reward do I earn?**
**How am I improving?**
**What can I try if this game is not fun for me?**

That is the core retention loop.
